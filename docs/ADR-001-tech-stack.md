# ADR-001: 技术栈选型

## Status
Proposed — 等你确认后转为 Accepted

## Context

约束：只安卓 / 数据全本地 / 不登录 / 不联网。
额外的人的约束（比技术约束更重要）：**用户不想碰代码**，工作方式此前已定为
「先做手机浏览器能打开的预览版确认功能与布局，确认后再打包 APK」。

这意味着：反馈循环的长度，比运行性能更重要。

## Options

### 选项 A：Web 技术 + Capacitor 壳（HTML/CSS/JS，无框架或轻量框架）

- 预览版就是成品逻辑，浏览器里刷新即见
- 打包：Capacitor 套安卓 WebView 壳
- 存储：预览用 IndexedDB，成品用 SQLite 插件

### 选项 B：原生 Kotlin + Jetpack Compose + Room

- 体验最好，性能最高
- 用户看不到预览，每次改动都要 Android Studio 编译 + USB 装包

### 选项 C：Flutter

- 体验接近原生，但同样需要编译才能看到结果
- 用户需额外装 Flutter 环境

## Decision

**选 A。**

理由排序（重要性递减）：
1. **反馈循环最短**：我改一行 → 你刷新 → 立刻看到。B/C 每次验证都要几分钟编译装包，一个功能返工三轮就是半小时。
2. 用户零环境负担：不需要装 Android SDK 就能先看东西（打包时才需要）。
3. 本项目数据量极小（10 年 1.8 万条），性能完全不是瓶颈，B/C 的性能优势用不上。

## Consequences

**变得更容易：**
- 快速迭代、预览即所得、用户能自己改文案和颜色
- 界面调整成本极低

**变得更难 / 放弃了什么：**
- 存储需要写两套适配器（IndexedDB / SQLite），有行为不一致风险 → 用统一的 Repository 接口 + 双适配器自动化测试缓解
- 性能上限低于原生（本项目用不到）
- 引入了一个第三方壳（Capacitor），需要审计它是否联网 → 不申请 INTERNET 权限，系统级阻断
- 数据库迁移要自己做（Room 有现成迁移框架，Web 侧没有）

**如果什么时候该推翻这个决定：**
当出现"必须原生能力"的需求（比如桌面小组件、快捷磁贴、后台常驻记账提醒）时，
再考虑用原生模块补齐，而不是整体重写。
